# Roadmap ideas: capture, place, and plan against the graph

The roadmap is a git repo of idea files forming a dependency graph.
Each idea is one file, `ideas/<id>.md`, with frontmatter (`status`, `depends_on`). The format is in the roadmap repo's `README.md`.
`GRAPH.md` is generated by `bun scripts/graph.ts`. Never edit it by hand.

This skill ships its own pieces. Adapt any of it to the project: the script, the idea format, the statuses, the area values and the commit policy are all starting points, not requirements.

- `scripts/graph.ts`: reads `ideas/*.md`, validates ids, statuses, missing dependencies and cycles, and writes `GRAPH.md`. `--check` validates without writing. Needs only Bun.
- `template/`: a starter roadmap repo (`README.md` with the idea format, and one example idea).

## Setup

- **Locate the roadmap.** Use the path in the project's CLAUDE.md or memory (the default is `~/roadmap`). If none is recorded, ask once with `AskUserQuestion` for the local path and the remote, then offer to record it.
- **Bootstrap if it doesn't exist.**
  1. Create the directory and copy `template/*` into it.
  2. Copy `scripts/graph.ts` to `<roadmap>/scripts/graph.ts`.
  3. Delete `ideas/example-idea.md` once a real idea exists.
  4. `git init`, set the remote if there is one, run `bun scripts/graph.ts`, and make the first commit.
- **Scope and areas.** Read the roadmap `README.md` for what it covers and what the `area` values are. If the user's idea is out of scope, say so and ask where it belongs.
- **Commit policy.** Follow the roadmap repo's own rules. If it's a personal scratch repo, commit and push straight to the default branch. If it has branch protection or review rules, use a branch and a PR.
- Start every invocation with `git -C <roadmap> pull -q --rebase` (skip if there is no remote).

## Planning against the roadmap (before any plan or design)

Whenever you are about to write a plan, spec, or non-trivial design, even if the user never mentioned the roadmap:

1. **Pull, then read `GRAPH.md` and skim the ideas near the work.** Find ideas that (a) this work is a prerequisite for, (b) this work depends on, (c) overlap with it, or (d) conflict with the approach you're leaning toward.
2. **Design for what's coming, build only what's asked.**
   - Pick interfaces, data shapes, naming and boundaries so downstream ideas fit without rework. Don't paint the next idea into a corner.
   - Do **not** build fields, flags, abstractions or extension points for those ideas. Future-proofing shapes the design; it doesn't add speculative code.
3. **Cite the ideas in the plan.** Add a short "Roadmap fit" section: the idea ids touched, how the design accommodates them, what was deliberately left out, and any conflict found.
4. **Surface conflicts, don't resolve them silently.** If the work contradicts, duplicates or reorders roadmap ideas, tell the user and ask via `AskUserQuestion`.
5. **Update the graph when the plan changes it.** A new dependency, an idea now unblocked, a scope split or merge: update the idea files in the same session, regenerate, commit and push.

Skip this only for trivial changes (typo, one-line fix, dependency bump) with no design surface.

## `/idea <text>`: capture

1. **Read the graph first.** Read `GRAPH.md` and skim the existing `ideas/*.md`. If the idea is really an existing one, offer to extend that file rather than start a new one.
2. **Flesh it out briefly.** Pitch in 2–4 sentences, "why" in 1–3. The user's own words win; don't inflate them.
3. **Do light research, about 5 minutes and no more.**
   - Look at the relevant code for what already exists, what's half-built, and which seams the idea would use.
   - Check open PRs and existing plans.
   - Web-search only where outside facts matter (limits, pricing, prior art).
   - Write findings under `## Research` as short bullets with `file:line` or links.
   - Never read production data for this.
4. **Ask 2–4 sharp questions** with `AskUserQuestion`.
   - Ask only what changes scope, dependencies or order.
   - Recommend an answer for each.
   - Record answers under `## Open questions` as `Q → A`; leave unanswered ones there.
5. **Place it in the graph.**
   - `depends_on`: the ideas that must be *done* first.
   - Where this idea unblocks an existing one, add it to that idea's `depends_on`.
   - Size: S/M/L/XL.
   - Status: `idea` while questions are open, `fleshed-out` once answered and researched.
   - The id is short kebab-case and must equal the file name.
6. **Generate, commit and push.** Run `bun scripts/graph.ts`; it fails on missing deps, cycles, id/file-name mismatches and unknown statuses. Fix and rerun until it passes. Then commit (`idea: <title>`) and push per the commit policy.
7. **Reply in three lines or fewer:** the idea, where it sits (blocked by X, unblocks Y), and a link to the idea file.

## `/idea list` and `/idea next`

- **list:** summarize `GRAPH.md` as in-progress, ready to start, and blocked, with what each is waiting on.
- **next:** recommend 1–3 ready ideas to start and why: what each unblocks, and its size.

## `/idea update <id> <change>`

Change status, add links (PRs, plans) or record answers. Mark an idea `done` only when its work has merged *and* shipped. Regenerate, commit and push.

## Keeping it current

When work tracked in the roadmap changes state elsewhere (a PR merges, a release ships, a plan is approved), update the matching idea in the same session.
